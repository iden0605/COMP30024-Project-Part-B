1. Approach

1.1 Search Algorithm

We implement minimax search with alpha-beta pruning to a fixed depth of 3 plies. The algorithm
searches from our agent's perspective (maximising player), modelling the opponent as a
minimising player. Alpha-beta pruning eliminates branches where the current path cannot
improve on an already-found bound, reducing the effective tree size without affecting the
selected action.

Each stack generates at most 12 candidate actions (3 types x 4 directions), so with n stacks
in play the branching factor is at most b = 12n. In the early play phase with 4 stacks per side,
b ≈ 48. Worst-case node count at depth 3 is O(b^3) ≈ 110,000. With perfect move ordering,
alpha-beta reduces this to O(b^(3/2)) ≈ 330 in the best case. In practice, move ordering
(Section 1.2) achieves close to best-case reduction, keeping per-turn search well within the
180-second CPU budget. As stacks merge or are eliminated, n falls and late-game search
becomes cheaper accordingly.

Terminal states short-circuit evaluation at any depth: +INF is returned immediately if the
opponent has no tokens, -INF if we do. If a position has no legal actions, 0 is returned
(stalemate draw).


1.2 Move Ordering

Before expanding children at any node, actions are sorted: EAT first, CASCADE second, MOVE
last. EAT actions directly reduce the opponent's token count and tend to produce high-scoring
positions, so evaluating them first tightens alpha and beta bounds early, pruning more of the
remaining subtree. CASCADE is placed second as it can push stacks off the board and
significantly reorganise position. MOVE is tried last as it is the least immediately impactful.


1.3 Evaluation Function

Non-terminal board states are scored using a linear weighted sum of three features:

    EVAL(s) = W_TOKENS x token_diff + W_HEIGHTS x height_diff + W_THREATS x threat_diff

[TABLE]
Feature | Weight | Computation | Strategic Motivation
token_diff | 10 | sum(my heights) - sum(opp heights) | Tokens are the win condition; their advantage is the primary metric
height_diff | 3 | max(my heights) - max(opp heights) | A tall stack can EAT any adjacent stack of height <= h and CASCADE h cells; rewards building a dominant stack
threat_diff | 2 | my eat threats - opp eat threats | Penalises positions where the opponent holds immediate EAT opportunities against our stacks
[/TABLE]

token_diff carries the highest weight because eliminating all opponent tokens is the only win
condition. height_diff uses maximum stack height rather than sum, since a single tall stack has
outsized tactical value: a stack of height h can cascade h cells and eat any adjacent stack of
height <= h. Rewarding max height encourages building one powerful stack. threat_diff counts,
for every adjacent pair of stacks, whether an EAT is currently legal; a negative value
signals we are about to lose tokens, so the agent steers away from such positions.

Weight selection is discussed in Section 2.1.


1.4 Placement Strategy

During the placement phase (4 turns each), each valid cell is scored as:

    score = -2 x center_dist + 0.5 x spread

where center_dist is the Manhattan distance from the cell to the board centre (3.5, 3.5),
and spread is the minimum Manhattan distance from the candidate to any existing friendly stack.
Cells closer to the centre are preferred as they have reach in all four directions from the
outset. The spread term discourages clustering, distributing stacks across the board to
maximise coverage entering the play phase.


2. Performance Evaluation

2.1 Evaluation Weight Tuning

To select evaluation weights, we wrote a tuning script (tune_weights.py) that systematically
tested combinations of W_HEIGHTS and W_TOKENS against a tokens-only baseline (W_TOKENS=10,
W_HEIGHTS=0, W_THREATS=0) over 2 games per combination. W_TOKENS was held fixed at 10
throughout. The 3 x 3 win rate grid below shows results across W_HEIGHTS in {0, 3, 6} and
W_THREATS in {0, 2, 5}:

[TABLE - Phase 1: Win rate vs tokens-only baseline]
W_HEIGHTS \ W_THREATS | 0    | 2    | 5
0                     | 0.50 | 0.50 | 1.00
3                     | 1.00 | 1.00 | 1.00
6                     | 1.00 | 1.00 | 1.00
[/TABLE]

Any combination with W_HEIGHTS >= 3 consistently beat the baseline, confirming that height
awareness is the most impactful additional feature. The (0, 5) result shows a high threat
weight can compensate partially for the lack of height feature.

Since multiple combinations achieved 100% against the baseline, we ran head-to-head games
between the 100% performers and our current configuration (10, 3, 2):

[TABLE - Phase 2: (10, 3, 2) head-to-head vs other 100% performers]
Opponent (W_TOKENS, W_HEIGHTS, W_THREATS) | W | L | D
(10, 0, 5)                                | 1 | 1 | 0
(10, 3, 0)                                | 0 | 0 | 2
(10, 3, 5)                                | 0 | 0 | 2
(10, 6, 0)                                | 2 | 0 | 0
(10, 6, 2)                                | 2 | 0 | 0
(10, 6, 5)                                | 1 | 0 | 1
[/TABLE]

The key finding is that W_HEIGHTS = 6 is consistently beaten by W_HEIGHTS = 3. Overweighting
stack height leads the agent to pursue aggressive stacking at the cost of total token count,
which is ultimately what determines the winner. W_HEIGHTS = 3 strikes the right balance:
it rewards building a strong stack without neglecting token parity.

The threat weight (W_THREATS = 2) draws consistently against W_THREATS = 0 and W_THREATS = 5
at W_HEIGHTS = 3, suggesting that within this region the exact threat weight is less critical.
We retain W_THREATS = 2 as a small positive contribution to defensive awareness. Our final
weights are confirmed as (W_TOKENS=10, W_HEIGHTS=3, W_THREATS=2).


2.2 Comparison with Monte Carlo Tree Search

We implemented a basic Monte Carlo Tree Search (MCTS) agent (mcts_agent/) for comparison.
MCTS builds a search tree using repeated simulations: the UCB1 formula selects which child
to explore, a random rollout of 20 steps estimates position quality, and results are
backpropagated through the tree. Selection, expansion, and backpropagation follow standard
two-player MCTS with result flipping at each level.

Each MCTS move was given 0.2 seconds of CPU time. We then ran 10 head-to-head games
alternating which agent played RED, using our benchmark script (benchmark.py):

[TABLE - Alpha-Beta vs MCTS over 10 games]
Result          | Count | Avg game time
Alpha-Beta wins | 10    | 12.8s
MCTS wins       | 0     | —
Draws           | 0     | —
[/TABLE]

Alpha-beta won all 10 games decisively. The core reason is that random rollouts are
uninformative in Cascade. In a game where strategic value comes from relative token counts,
stack heights, and eat threats, random play produces noisy position assessments that do not
reliably indicate which positions are winning. Alpha-beta's explicit evaluation function
captures these features directly, resulting in consistently better decisions at comparable
compute budgets. MCTS is further disadvantaged by Cascade's large branching factor
(b ≈ 48), which limits the number of rollouts per move.


3. Other Aspects

3.1 Board Representation

The board is stored as a sparse dict {Coord: CellState}, matching Part A. Only occupied
cells are present; empty cells are absent. Dict lookup and insertion are O(1) average, and
copying the board per search node takes O(k) where k is the number of occupied cells
(at most 8 after placement, falling as stacks are eliminated). This keeps per-node overhead
low throughout the search tree.

3.2 Terminal Detection Depth Independence

Terminal state checks run before the depth cutoff: if either player has zero tokens, the
result is returned immediately regardless of depth. This ensures wins and losses deep in the
tree are correctly identified and propagated, not mistakenly treated as non-terminal.

3.3 Alpha-Beta vs Pure Minimax

Alpha-beta pruning achieves significant node reduction over pure minimax. In the ideal case
(perfect move ordering), node count reduces from O(b^d) to O(b^(d/2)). At b = 48 and d = 3,
this is the difference between ~110,000 and ~330 nodes per search call. Move ordering
by action type (EAT > CASCADE > MOVE) approximates this ideal, as aggressive actions tend
to produce the highest scores and so tighten bounds fastest.


4. Supporting Work

We developed two supporting scripts to assist in agent evaluation:

benchmark.py simulates full games directly between two agent classes without the referee
subprocess, enabling rapid head-to-head testing. Games are simulated by applying actions to
a shared board dict and checking win conditions after each turn. The script accepts a game
count argument and reports per-game outcomes and a summary.

tune_weights.py tests evaluation weight combinations systematically. For each (W_HEIGHTS,
W_THREATS) pair, it constructs an agent variant using a closure over a parameterised evaluate
function and runs it against the tokens-only baseline. Results are printed as a win-rate table.
This script was used to generate the tuning data in Section 2.1 and directly informed our
final weight selection.
